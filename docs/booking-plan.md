# Booking System — Πλάνο (custom, στο δικό μας stack)

> Online ραντεβού **φτιαγμένο από εμάς** (όχι SimplyBook), πάνω στο υπάρχον Next.js + Supabase + /admin + Resend. Σχεδιασμένο για τη **μοναδική** φύση του business: **σόλο επαγγελματίας που πάει κατ' οίκον**.

> **🚧 Κατάσταση (branch `feature/booking-system`):**
> - ✅ **Phase 1 (MVP)**: DB schema · availability engine (Athens TZ) · `/booking` flow · emails · `/admin/bookings` (confirm/cancel). Mode = **προς-έγκριση**· placeholder ωράρια/διάρκειες (ο πελάτης επιβεβαιώνει).
> - ✅ **Phase 2**: **area-aware travel buffer** · **self-service ακύρωση** (signed link `/booking/manage`, no login) · **auto-υπενθυμίσεις** (daily GitHub Action ~24h πριν, με cancel link).
> - ✅ **Phase 3 (κώδικας έτοιμος, pending creds)**: **Google Calendar sync** (service account → events στο κινητό του) · **optional deposit με Viva** (Smart Checkout + return page). Graceful no-op μέχρι να μπουν τα creds. *(SMS/σειρές/intake/ιστορικό — απορρίφθηκαν από πελάτη.)*
> - 🔌 **Wiring**: τα «Κλείστε ραντεβού» CTAs → `/booking` (όταν δοθεί ΟΚ).

## 0. Γιατί ΔΕΝ είναι «κλασικό» booking (η ιδιαιτερότητα)
Ο Δανάλης δεν έχει ιατρείο με αίθουσες — **πάει σπίτι του ασθενή** σε Γλυφάδα/Βούλα/Βουλιαγμένη/Βάρη/Άλιμο. Αυτό αλλάζει τα πάντα:

1. **Μετράει η μετακίνηση** — δεν μπορεί 17:00 Βούλα και 17:30 Άλιμο. Το σύστημα **πρέπει** να υπολογίζει χρόνο μετακίνησης.
2. **Ένα ημερολόγιο** (ένας άνθρωπος) — όχι resources/αίθουσες. Απλούστερο σε ένα σημείο, αλλά κρίσιμο να μη γίνει double-book.
3. **Διεύθυνση = κρίσιμο πεδίο** — το ραντεβού γίνεται στη διεύθυνση του ασθενή.
4. **Μεταβλητή διάρκεια** ανά υπηρεσία (χιροπρακτική 45′, λεμφικό 75′, αξιολόγηση 60′…).
5. **Σειρές συνεδριών** — η φυσικοθεραπεία είναι συχνά «πακέτο» 6-10 συνεδριών, όχι one-off.
6. **No-show κοστίζει διπλά** — έχασε και τον χρόνο και το ταξίδι.

→ Άρα δεν θέλουμε ένα γενικό calendar widget· θέλουμε **booking που «καταλαβαίνει» μετακίνηση + περιοχές + σειρές**.

## 1. Πώς θα δουλεύει — πλευρά ΑΣΘΕΝΗ (το flow)
Στο site, κουμπί «Κλείστε ραντεβού» → σελίδα `/booking`:

1. **Υπηρεσία** → διαλέγει (π.χ. «Χιροπρακτική κατ' οίκον») — βλέπει διάρκεια & σύντομη περιγραφή.
2. **Περιοχή** → Γλυφάδα/Βούλα/Βουλιαγμένη/Βάρη/Άλιμο (καθορίζει διαθεσιμότητα + μετακίνηση).
3. **Διαθέσιμες ώρες** → ένα ημερολόγιο δείχνει **μόνο** ελεύθερα slots (αφού αφαιρεθούν κλεισμένα ραντεβού + ωράριο + buffers μετακίνησης + ρεπό).
4. **Στοιχεία** → όνομα, τηλέφωνο, **διεύθυνση**, σύντομη περιγραφή προβλήματος, «πρώτη φορά;».
5. **Επιβεβαίωση** → instant ή «αίτημα προς έγκριση» (βλ. §3).
6. **Υπενθυμίσεις** → email/SMS/Viber πριν το ραντεβού.

## 2. Πώς ΔΙΕΥΚΟΛΥΝΕΙ τον Δανάλη (η καρδιά του πράγματος)
Είναι σόλο → το σύστημα γίνεται ο **24/7 γραμματέας** του:

| Πρόβλημα σήμερα | Με το booking |
|---|---|
| Τηλεφωνική γραμματεία, χαμένες κλήσεις, μηνύματα εκτός ωραρίου | Οι ασθενείς κλείνουν **μόνοι τους, 24/7**, χωρίς τηλέφωνο |
| Κίνδυνος double-booking / μπερδέματα | Τα slots κλειδώνουν **αυτόματα** — αδύνατο 2 ραντεβού ίδια ώρα |
| Αδύνατα back-to-back σε μακρινές περιοχές | **Buffer μετακίνησης** μπαίνει αυτόματα — ποτέ αδύνατη διαδρομή |
| Φτάνει χωρίς πληροφορίες | Έχει **εκ των προτέρων**: διεύθυνση, πρόβλημα, τηλέφωνο → ετοιμάζεται + ξέρει τη διαδρομή |
| No-shows | **Αυτόματες υπενθυμίσεις** (24ω + 2-3ω πριν) → λιγότερες ακυρώσεις |
| Όλα στο μυαλό/χαρτί | **Συγχρονισμός με Google Calendar** του → τα βλέπει στο κινητό· μπλοκάρει ώρες με ένα tap |
| Επαναλαμβανόμενοι ασθενείς | **Ιστορικό** + εύκολο κλείσιμο **σειράς συνεδριών** |
| Χάνει ώρες σε admin | Λιγότερος χρόνος διαχείρισης → **περισσότερες συνεδρίες/μέρα** |

**Με μια φράση:** μετατρέπει το «τηλέφωνο + ημερολόγιο στο χέρι» σε **αυτοματοποιημένη ροή** που του γεμίζει την ατζέντα έξυπνα και του γλιτώνει διαδρομές.

## 3. Τα «έξυπνα» χαρακτηριστικά (αυτά που το κάνουν να αξίζει custom)

**🚗 Travel-aware scheduling** (το πιο σημαντικό)
- **Travel buffer**: αυτόματα X′ ανάμεσα σε ραντεβού. Configurable.
- **Area-aware**: ίδια περιοχή = μικρό buffer (15′)· διαφορετική = μεγάλο (45′). Μικρός «πίνακας αποστάσεων» μεταξύ των 5 περιοχών.
- **(Προχωρημένο) Area-days**: «Δευτέρα Γλυφάδα/Βούλα, Τρίτη Βάρη/Βουλιαγμένη…» → το booking δείχνει slots **μόνο** στην περιοχή της ημέρας → **clustering διαδρομών** = λιγότερο οδήγημα, περισσότερα ραντεβού.

**⏱️ Διάρκεια ανά υπηρεσία** — κάθε υπηρεσία έχει δική της διάρκεια → το slot προσαρμόζεται.

**🔁 Σειρές / πακέτα** — κλείσιμο «10 συνεδρίες, κάθε Τρίτη 18:00» με μία κίνηση (το rehab είναι σειρά).

**✅ Instant vs «προς έγκριση»** — υβριδικό: **νέοι** ασθενείς ή ασυνήθεις περιοχές → αίτημα που εγκρίνει ο Δανάλης (ελέγχει εφικτότητα/διαδρομή)· **γνωστοί/τυπικά** → instant. Ισορροπία ευκολίας & ελέγχου.

**🔔 Υπενθυμίσεις & no-show προστασία** — email (δωρεάν) + ιδανικά **SMS/Viber** (οι Έλληνες ζουν στο Viber). Link «επιβεβαίωση/ακύρωση». *(Προαιρετικά αργότερα: προκαταβολή/κάρτα για no-shows — ευαίσθητο, μελλοντικό.)*

**📝 Intake νέου ασθενή** — πρόβλημα, ιστορικό, φάρμακα, σημείωση parking → φτάνει προετοιμασμένος.

**🚫 Block-off** — ρεπό, διακοπές, προσωπικός χρόνος → δεν εμφανίζονται ως διαθέσιμα.

## 4. Τεχνική αρχιτεκτονική (πάνω στο ΥΠΑΡΧΟΝ stack — όχι από το μηδέν)

- **Supabase** (το έχουμε): πίνακες `services` (διάρκεια, περιγραφή), `appointments`, `availability_rules` (ωράριο, area-days), `time_off`, `patients` (ιστορικό).
- **Next.js**: δημόσια σελίδα `/booking` (slot picker) + **calendar view στο υπάρχον `/admin`** (ο Δανάλης βλέπει/διαχειρίζεται).
- **Availability engine** (η «μαγεία»): ελεύθερα slots = ωράριο − κλεισμένα − ρεπό − **travel buffers** − area rules. Pure logic, server-side.
- **Notifications**: **Resend** (email — το έχουμε) για επιβεβαιώσεις/υπενθυμίσεις· SMS/Viber μέσω παρόχου (π.χ. Twilio/Vonage) αν θέλει.
- **Reminders cron**: GitHub Action (όπως το blog) στέλνει υπενθυμίσεις 24ω/2-3ω πριν.
- **Google Calendar 2-way sync** (προαιρετικό, υψηλής αξίας): ραντεβού → ημερολόγιό του στο κινητό· μπλοκ από το ημερολόγιό του → κλειστή διαθεσιμότητα.
- **Auth/admin**: ήδη υπάρχει (password login) — απλώς προσθέτουμε το calendar module.
- **SEO**: `Reservation`/`Schedule` schema + το `/booking` ως conversion page.

## 5. Custom vs SimplyBook — γιατί custom ταιριάζει εδώ
| | Custom (εμείς) | SimplyBook |
|---|---|---|
| **Travel/area logic** | ✅ Ακριβώς για κατ' οίκον | ❌ Γενικό, δύσκολα |
| Design/brand | ✅ 100% στο site | ⚠️ iframe widget |
| Δεδομένα ασθενών | ✅ Δικά μας (Supabase) — GDPR control | ⚠️ Σε τρίτο |
| Μηνιαίο κόστος | ✅ Μηδέν (πληρώνεις μόνο SMS αν θες) | 💰 Συνδρομή |
| Ενσωμάτωση με blog/admin/email | ✅ Ένα σύστημα | ❌ Ξεχωριστό |
| Κόστος | ⏱️ Χρόνος ανάπτυξης (αλλά πάνω στο υπάρχον stack) | Γρήγορο setup |

→ Για **κατ' οίκον σόλο** με ανάγκη travel-logic + brand + δεδομένα, το **custom** δίνει σαφώς καλύτερο αποτέλεσμα.

## 6. Φάσεις (MVP → πλήρες)

**Phase 1 — MVP (λειτουργικό booking)**
Services+διάρκεια · εβδομαδιαίο ωράριο · slot picker · booking → Supabase + email στον Δανάλη + επιβεβαίωση στον ασθενή · calendar list στο /admin · χειροκίνητο confirm/cancel. **Fixed travel buffer.**

**Phase 2 — Αυτοματισμοί**
Auto υπενθυμίσεις (email) · links reschedule/cancel · **Google Calendar sync** · area-aware buffers.

**Phase 3 — Έξυπνα/premium**
Area-days clustering · σειρές/πακέτα · SMS/Viber υπενθυμίσεις · intake νέου ασθενή · ιστορικό ασθενών · (προαιρετικά) προκαταβολή no-show.
